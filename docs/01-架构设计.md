| # | 项 | 结论 | 理由 |

| 1 | Web 框架 | FastAPI ✅ 采纳 | 原生 async、Pydantic 强校验、自动 OpenAPI，与「前后端数据结构必须一致」的要求天然契合 |

### 1.2 关键架构原则（贯穿全项目，也是面试可讲点）

| 原则 | 落地方式 |
|---|---|
| **单一状态机入口** | 所有任务状态变更只能通过 `ReviewTaskService.transition(to_status, reason)`，内部校验合法性 + 写 `task_event`。禁止任何地方直接 `task.status = xxx` |
| **能力域可替换** | 解析器、OCR、LLM、审批客户端全部面向抽象接口编程，实现类通过配置注入（工厂 + settings 开关） |
| **统一坐标系** | 一切定位（风险、建议、批注、元数据）都落在同一个「归一化文本流全局字符偏移」坐标系上，见 §10.3 |
| **LLM 只出结构化数据** | Provider 层强制 schema 校验，输出 Pydantic 对象；前端永远不解析自然语言 |
| **LLM 不许自报坐标** | LLM 只允许 `quote` 原文片段，`char_start/char_end` 由后端在原文中反查回填，杜绝幻觉偏移 |
| **幂等优先** | 任务执行、回写、报告生成全部带幂等键 |
| **可观测** | 结构化日志 + `task_event` 时间线 + `ai_call_log` 每次模型调用全量留痕 |
| **锁不跨长任务** | DB 行锁只覆盖"抢任务"这一次 UPDATE，OCR/LLM 全程在事务外执行（§1.4） |

### 1.3 并发模型：async / to_thread / 进程池 的边界（关键）

Worker 是单个 asyncio 事件循环。**任何同步阻塞调用都会卡死整个 event loop**，导致心跳停止、所有在跑任务被自愈机制误判为卡死。因此必须显式划分三类操作：

| 类别 | 具体操作 | 执行方式 | 理由 |
|---|---|---|---|
| **原生 async** | LLM HTTP 调用（httpx.AsyncClient / anthropic AsyncClient）、数据库读写（asyncmy + SQLAlchemy async）、附件下载 | `await` 直接跑在 event loop | I/O 密集，await 期间让出控制权，天然并发 |
| **同步阻塞 I/O** | `python-docx` 读文件、PyMuPDF 打开/抽取/渲染、本地文件读写、Playwright 调用 | `await asyncio.to_thread(...)` | 这些库是 C 扩展且无 async 版本，必须扔默认线程池（`min(32, cpu+4)`） |
| **CPU / Native 密集** | OCR 推理（RapidOCR/onnxruntime）、图像预处理（灰度/二值化/去噪）、大页渲染 | 默认独立 `ProcessPoolExecutor`（`OCR_MAX_WORKERS` 默认 **1**，可配 1/2/4），**懒加载**；可配置切回线程池 | OCR 属于秒级 CPU/Native 计算任务，独立进程可避免长时间计算与 Worker event loop 调度争用；**实际基准测试允许切换为线程池**（见下方 `OCR_EXECUTOR_MODE`） |

**7 条硬规则（写进代码规范，Code Review 检查项）：**

1. **OCR 默认走进程池**：`await loop.run_in_executor(ocr_pool, engine.recognize, img_path)`。OCR 属于秒级 CPU/Native 计算任务，独立进程可避免长时间计算与 Worker event loop 调度争用。
   - **懒加载（lazy init）**：worker 启动时**不**创建 OCR 进程池，首次真正遇到需要 OCR 的文件时才创建（`ensure_ocr_pool()` + 双检锁，保证只创建一次）。黄金链路只跑 DOCX，**P2 不会提前拉起一个永不使用的 OCR 进程池**。
   - **并发度受控**：`OCR_MAX_WORKERS` 默认 **1**，可配置 1 / 2 / 4。默认取 1 是为了避免 `Worker 数 × 进程池大小` 的进程爆炸（2 个 worker × 4 = 8 个常驻进程，且各自加载一份 OCR 模型）。
   - 每个子进程内各自初始化一份 OCR session，避免每页重复加载模型。
2. **`OCR_EXECUTOR_MODE` 可配置**：`process`（默认）/ `thread`。用进程池的理由是避免与 event loop 调度争用；**若实测（如 onnxruntime 已充分释放 GIL、或单核受限机器上进程调度开销更大）线程池表现更好，可切到 `thread`，无需改代码**。这个开关的存在本身就是"用基准测试说话、而非拍脑袋"的体现。
3. **解析库一律走默认线程池**：`await asyncio.to_thread(parser.parse, path)`。PyMuPDF 的 `fitz.open` 对象**不能跨线程共享**，必须保证"打开 → 解析 → 关闭"在同一个线程内完成。
4. **DB session 绝不进线程池**：SQLAlchemy `AsyncSession` 绑定 event loop，只允许在 event loop 内的协程中使用。解析函数若需落库，必须返回纯数据 DTO，回到 event loop 后再写。
5. **心跳与主流程解耦**：心跳由独立的 asyncio 后台任务每 30s 写一次，**不依赖主流程推进**。即使 OCR 在某页卡了 2 分钟，心跳仍在跳，不会被误判为卡死。
6. **并发上限可配**：同一时刻跑 `WORKER_CONCURRENCY`（默认 2）个任务，每个任务内部阶段串行；REVIEW 阶段的多批 LLM 调用用 `asyncio.Semaphore(4)` 限流并发。
7. **执行器降级**：若 `ProcessPoolExecutor` 创建失败（受限环境），自动降级为 `to_thread` 并记 warn 日志 —— 功能不中断，性能下降。

PARSE 阶段的实际调用形态（说明边界，非最终代码）：

```python
async def run_parse_stage(task_id: int, file: ContractFile) -> None:
    # 1. 同步阻塞 I/O → 默认线程池
    blocks_raw = await asyncio.to_thread(PARSER_REGISTRY[file.file_ext].parse, file.storage_path)

    if blocks_raw.needs_ocr:                        # 2. CPU 密集 → 独立进程池
        loop = asyncio.get_running_loop()
        blocks_raw = await loop.run_in_executor(ocr_pool, ocr_pages, blocks_raw.image_pages)

    blocks = TextNormalizer.normalize(blocks_raw)   # 3. 毫秒级纯内存计算 → 直接在 event loop 跑
    await save_blocks(blocks)                       # 4. async DB
    await run_metadata_and_clause_stage(...)        # 5. 内部 await LLM（async）
```

> 第 3 步的取舍值得说明：**不是所有 CPU 操作都要扔线程池**。判断标准是"单次耗时是否可感知（>10ms）且是否高频调用"。几万字符的归一化是毫秒级，扔线程池的调度开销反而更大；只有 OCR / 图像处理这种秒级 CPU 任务才需要进程池。这个判断本身就是面试可讲的点。

### 1.4 DB Queue 抢占的事务边界（关键）

**核心原则：锁只覆盖"抢任务"这一瞬间的 UPDATE，绝不跨越任何长耗时操作。**

```
┌──────────────────── 事务 T1（毫秒级，唯一持锁区间）────────────────────┐
│ BEGIN                                                                  │
│ SELECT id, contract_id, file_id, current_stage, retry_count            │
│   FROM review_task                                                     │
│  WHERE status = 'pending'                                              │
│    AND (next_retry_at IS NULL OR next_retry_at <= NOW(3))              │
│  ORDER BY priority DESC, id ASC                                        │
│  LIMIT 1                                                               │
│  FOR UPDATE SKIP LOCKED;   ← SKIP LOCKED：其它 worker 直接跳过被锁行    │
│                                                                        │
│ -- 未取到行 → COMMIT，sleep 后重试（空闲轮询，见下）                    │
│                                                                        │
│ UPDATE review_task                                                     │
│    SET status='parsing', worker_id=:wid, locked_at=NOW(3),             │
│        heartbeat_at=NOW(3), started_at=COALESCE(started_at,NOW(3)),    │
│        version=version+1                                               │
│  WHERE id=:id AND status='pending';   ← 双保险，rowcount 必须 = 1       │
│                                                                        │
│ INSERT INTO task_event(task_id, from_status, to_status, reason,        │
│                         operator)                                      │
│   VALUES (:id,'pending','parsing','worker_claimed',:wid);              │
│ COMMIT;   ← ★ 锁在此释放。此后 OCR / LLM 全部在事务外执行               │
└────────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──── 事务外：长耗时阶段（可能数分钟，期间不持有任何数据库行锁）────┐
│ 1. 启动心跳后台任务（每 30s 一条独立短事务：                       │
│    UPDATE review_task SET heartbeat_at=NOW(3)                     │
│     WHERE id=:id AND worker_id=:wid  → 立即 COMMIT）               │
│ 2. PARSE：OCR/解析（进程池/线程池）→ 完成后用独立短事务分批写       │
│    document_block / contract_metadata / clause                    │
│ 3. 阶段切换：独立短事务 UPDATE status='reviewing' + 写 task_event  │
│ 4. REVIEW：LLM 批量调用 → 逐批用独立短事务写 risk_item             │
│ 5. 收尾：独立短事务 UPDATE status='completed', finished_at + 事件   │
│ 6. finally：取消心跳；异常交 ErrorClassifier 决定 blocked / 重试    │
└───────────────────────────────────────────────────────────────────┘
```

**6 条硬规则：**

1. **锁的范围 = 一条 UPDATE**。`FOR UPDATE` 事务内**禁止**出现任何 `await` 的 I/O（LLM/OCR/文件下载/解析），禁止解析文件。
2. **`SKIP LOCKED` 只用于抢 `pending` 任务**。不要用它扫 `parsing/reviewing` —— 那是自愈扫描的职责，用普通查询 + 超时条件（§13.5）。
3. **状态二次校验**：`UPDATE ... WHERE id=:id AND status='pending'`，`rowcount != 1` 说明被他人抢走或状态已变，**静默放弃**本次任务继续下一轮，不报错。
4. **心跳必须是独立短事务**：独立 `async_session()`，UPDATE 完立即 commit，绝不与主流程共用一个长 session。
5. **每次落库都是独立短事务**：5000 个 block 不能一个事务写完，需分批 commit（每 500 条一次）。这既是避免长事务锁等待/undo 膨胀，也是**断点续跑**的前提 —— 已写入的部分不因后续失败而回滚。
6. **幂等兜底**：worker 崩溃导致状态卡在 `parsing` 时，自愈机制（§13.5）把超过 5 分钟无心跳的任务回退 `pending`；重跑时按 `contract_id + current_stage` 检查产物是否已存在，**已完成的阶段直接跳过**。

**空闲轮询策略**：未抢到任务时 `sleep(1s)`；连续 10 次空转后退避到 `sleep(5s)`；一旦抢到任务立即恢复 1s。避免空队列时空转打满 CPU 与数据库。

## 3. 模块之间的依赖关系

**依赖方向严格单向，禁止反向 import。**

```
api/endpoints  ──►  services  ──►  {parsers, rules, llm, integrations, reports}
                        │                        │
                        └──►  db/repositories ───┘
                                     │
                                  db/models ──► core/constants
```

允许与禁止：

| 规则 | 说明 |
|---|---|
| endpoints **只**做参数校验 + 调 service + 组装响应 | 禁止在 endpoint 里写业务分支、禁止直接查库 |
| services 之间可以互相调用，但**任务状态变更只能走 `ReviewTaskService`** | 防止状态机被绕过 |
| parsers / rules / llm / reports **不依赖 services** | 保证能力域可单测、可替换 |
| `llm/` 不感知数据库，输入输出都是纯 Pydantic 对象 | 便于 Mock 测试、便于换模型 |
| `integrations/` 只暴露 `ApprovalClient` 接口 | Mock 与真实实现同签名，切换只改配置 |
| workers **调用 services**，不直接写库 | 复用状态机与幂等逻辑 |

关键交叉依赖（必须说明清楚）：
- `workers/stages.py` → `DocumentService.parse()` → `parsers/*` → 落 `document_block`
- `workers/stages.py` → `RiskService.review()` → `rules/engine` + `llm/provider` → 落 `risk_item` / `risk_suggestion`
- `RiskService` → `ClauseService`（取条款）与 `MetadataService`（取主体信息做主体资质校验）
- `WritebackService` → `ReportService`（取摘要）+ `integrations/ApprovalClient`
- `frontend/api/types` ↔ `backend/schemas`：**字段名一一对应，是一份契约的两侧**；第二阶段会给出对照表并写进文档

## 4. 数据流

### 4.1 主数据流（端到端）

```
[业务经办人] 上传文件 ──┐
                        ├─► POST /contracts (multipart)
[Mock审批系统] 待办拉取 ─┘        │
                                  ▼
                        ContractService.create()

                        · 写 task_event
                                  │
                                  ▼

                                  │
                        [Worker 进程] DbQueueDispatcher 抢占
                        UPDATE review_task SET status='parsing', worker_id=...
                        WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED
                                  │
                                  ▼
        阶段 1 PARSE：解析 → OCR → 归一化 → 元数据 → 条款切分
        产物落库：document_block / contract_metadata / clause
        状态：parsing ──► reviewing
                                  │
                                  ▼
        阶段 2 REVIEW：
          2a 规则引擎逐条评估（确定性，快）
          2b LLM 分条款批量语义研判（结构化 JSON）
          2c 合并去重 → 风险评分 → 综合等级 → 摘要
          2d 生成修改建议（LLM 内联建议 + 标准条款库匹配）
        产物落库：risk_item / risk_suggestion
        状态：reviewing ──► completed
                                  │
                                  ▼
        [前端] 工作台打开：GET /tasks/{id}/document + /risks + /metadata
               原文高亮锚定（char_start_global / char_end_global）
                                  │
                                  ▼
        [法务审查人] 核对风险 → 采纳/编辑建议 → 写法务批注
                                  │
                                  ▼
        POST /tasks/{id}/writeback
        WritebackService：生成 Markdown 评论 → ApprovalClient.post_comment(幂等键)
        状态：not_written → writing → success / failed
                                  │
                                  ▼
        [业务经办人] GET /tasks/{id}/report/download?format=md|pdf
```

### 4.2 数据流中的三个关键「转换点」

1. **文件 → 归一化文本流**：产生 `document_block` 序列，每个 block 同时持有 `page_number`、`paragraph_index`、block 内偏移、**全局字符偏移**。
2. **条款 → 风险**：LLM 输出只带 `quote`，后端反查回填全局偏移，保证「风险卡片 ↔ 原文」永远能对上。
3. **审查结论 → 评论 Markdown**：写回内容是可追溯的纯文本快照（含风险清单 + 法务批注），落 `writeback_record.content_md` 存档，便于审计与重放。

## 5. 核心业务流程

### 5.1 审批触发与自动审查（流程 A）

1. 触发源二选一：① 用户在系统内上传；② 定时/手动拉取 Mock（未来真实）审批系统待办。
2. 拉取时按 `sync_cursor` 增量拉取，**先查 sha256 去重**，已存在的附件不重复下载。
3. 建任务 → 返回 `task_id`，前端拿到后进入工作台轮询。
4. Worker 执行 PARSE → REVIEW 两阶段。
5. 完成后任务 `completed`，前端轮询到终态后自动刷新风险列表。

### 5.2 法务人工复核与协同改写（流程 B）

1. 法务在工作台打开合同，左侧原文 + 右侧风险卡片。
2. 点击风险卡片 → 原文自动滚动到对应位置并高亮（`useHighlight`）。
3. 法务对每个风险点可执行：**确认** / **驳回（误报）** / **调整风险等级** / **编辑建议文本** / **重新生成建议**。
4. 法务写人工批注（可锚定到某个 block 或某个风险点）。
5. 点击「写回审批意见」→ 系统生成摘要 Markdown（含风险总评 + 重点关注 + 法务批注）→ 调用审批评论接口。
6. 回写结果轮询展示；成功后业务经办人可下载整改对比报告。

### 5.3 异常阻塞与重试（流程 C）

1. PARSE 阶段不可恢复错误（加密、空正文、扫描严重模糊、格式不支持）→ `blocked`，记录 `block_reason_code` + 人话原因。
2. REVIEW 阶段系统级错误（LLM 连续超时/5xx 超阈值）→ 自动重试耗尽后 `blocked`。
3. 管理员在任务监控页看到阻塞列表 → 查看原因 → 可「修正文件/调整参数」→ 点击「重新审查」→ `blocked → pending`（`retry_count+1`）。
4. 重试时**断点续跑**：PARSE 阶段产物若已完整落库则跳过解析，直接进 REVIEW。

## 6. 状态机设计

### 6.1 任务状态机（review_task.status）

```
                    ┌──────────────────────────────────────┐
                    │                                      │
                    ▼                                      │
   [创建] ──►  pending ──► parsing ──► reviewing ──► completed(终态)
                 ▲            │            │
                 │            │            │
                 │            ▼            ▼
                 │         blocked ◄───────┘
                 │            │
                 └────────────┘  (管理员「重新审查」)
```

**合法迁移表（唯一权威，代码里用常量矩阵实现）**

| from \ to | pending | parsing | reviewing | blocked | completed |
|---|---|---|---|---|---|
| pending | – | ✅ worker 抢占 | ❌ | ✅ 前置校验失败 | ❌ |
| parsing | ✅ 重试 | ✅ 心跳续期 | ✅ 解析成功 | ✅ 解析失败/超时 | ❌ |
| reviewing | ✅ 重试 | ❌ | ✅ 心跳/分批评审 | ✅ 重试耗尽 | ✅ 审查完成 |
| blocked | ✅ 人工重试 | ❌ | ❌ | – | ❌ |
| completed | ❌（重新审查=新建 task） | ❌ | ❌ | ❌ | – |

**为什么 completed 不可回退**：审查结论是审计证据，必须不可变。需要重新审查时**新建一个 task**，`contract.current_task_id` 指向最新，历史任务与历史结论全部留存 —— 这是面试可讲的「审计友好」设计。

**阶段级断点字段**：`current_stage` ∈ {UPLOADED, PARSED, CLAUSED, REVIEWED}，用于断点续跑。

**状态变更的执行方式**（与 §1.4 对应）：
- `pending → parsing` 在**抢占事务 T1 内**完成（一条 UPDATE + 一条 task_event，随即 commit）。
- 其余迁移（`parsing→reviewing`、`→completed`、`→blocked`、`blocked→pending`）都是**独立短事务**，每条都是一个 `transition()` 调用 + 一条 task_event。
- 所有 UPDATE 都带 `WHERE id=:id AND status=:expected_from`（乐观校验）并 `version=version+1`，防止并发下状态被覆盖。

**block_reason_code 枚举**（枚举化才能做统计与自愈）：
`FILE_ENCRYPTED` / `FILE_CORRUPTED` / `UNSUPPORTED_FORMAT` / `EMPTY_TEXT` / `OCR_FAILED` / `OCR_LOW_QUALITY` / `LLM_UNAVAILABLE` / `LLM_SCHEMA_INVALID` / `TIMEOUT` / `INTERNAL_ERROR`

### 6.2 回写状态机（writeback_record.status）

```
not_written ──► writing ──► success (终态)
                   │
                   └──► failed ──► writing (重试, attempt+1)
```

| from \ to | writing | success | failed |
|---|---|---|---|
| not_written | ✅ 用户点击写回 | ❌ | ❌ |
| writing | – | ✅ 接口 2xx | ✅ 超时/4xx/5xx |
| failed | ✅ 重试 | ❌ | – |
| success | ❌ 幂等锁定 | – | – |

**幂等键**：`idempotency_key = sha256(task_id + content_md_hash)`。同内容重复提交，审批系统侧返回既有评论（Mock 会模拟这一行为），本地直接返回上次结果，不产生第二条评论。

### 6.3 风险复核状态（risk_item.review_status）

```
PENDING（AI 产出，未复核）
  ├─► CONFIRMED（法务确认）
  ├─► REJECTED （法务判定误报，不计入综合结论）
  └─► MODIFIED （法务调整了等级或建议）
```

综合风险等级**基于有效风险**（排除 REJECTED）重新计算，且 `MODIFIED` 以人工等级为准。

## 9. AI 审查流程

### 9.1 LLM Provider 抽象设计（你特别要求的）

```
                    ┌──────────────────────────────┐
                    │      LLMProvider (ABC)       │
                    │──────────────────────────────│
                    │ chat(req: LLMRequest)        │
                    │   -> LLMResult               │
                    │ health_check() -> bool       │
                    │ supports_structured_output() │
                    └───────┬──────────────┬───────┘
                            │              │
              ┌─────────────▼───┐   ┌──────▼─────────────┐
              │ DeepSeekProvider│   │ AnthropicProvider  │
              │ (OpenAI 兼容协议)│   │ (官方 anthropic SDK)│
              │ 默认结构化输出:   │   │ 结构化输出:          │
              │ json_object 模式 │   │ output_config.format│
              └─────────────────┘   └────────────────────┘
                            │
                    ┌───────▼──────────────────────┐
                    │ LLMFactory.build(settings)   │  ← 按配置切换，业务代码零改动
                    └──────────────────────────────┘
```

**统一请求/响应契约**

```python
class LLMRequest(BaseModel):
    scene: str                  # CLAUSE_REVIEW / METADATA_EXTRACT / SUGGESTION / SUMMARY
    system_prompt: str
    user_prompt: str
    output_schema: type[BaseModel] | None   # 非空 = 要求结构化输出
    temperature: float = 0.2
    max_tokens: int = 4096
    timeout: float = 120.0
    prompt_version: str          # 写入 ai_call_log，便于效果回归对比

class LLMResult(BaseModel):
    parsed: BaseModel | None     # ✅ 已通过 Pydantic 校验的结构化对象
    raw_text: str                # 原始文本，留痕
    model: str; provider: str
    prompt_tokens: int; completion_tokens: int; latency_ms: int
    request_id: str
    attempts: int                # 实际尝试次数（含 JSON 修复重试）
```

**统一结构化输出保障链（`json_guard.py`，四道防线）**

1. **协议层**：DeepSeek 用 `response_format={"type":"json_object"}`；Anthropic 用 `output_config={"format": {...}}`（结构化输出，比让模型"自己注意 JSON"可靠得多）。
2. **提示层**：prompt 内嵌 JSON Schema 与字段说明 + 3 条硬性规则（只输出 JSON、不得编造条款、quote 必须逐字复制原文）。
3. **解析层**：剥 ```json 围栏 → `json.loads` → 失败则用「错误信息 + 原始输出」回灌模型做一次修复重试（≤2 次）。
4. **校验层**：Pydantic 严格校验（字段缺失/枚举越界/类型错误一律抛 `LLM_SCHEMA_INVALID`），校验失败同样走修复重试；**仍失败则本批降级为「仅规则引擎结果」并在任务上标记 warning，绝不让整个任务失败**。

> **阶段归属（与 §17 对齐）**：第 **1/2/4** 道防线属于 **P10，必须实现** —— 协议层约束 + 提示层 schema 说明 + Pydantic 校验，共同保证 LLM 输出是结构化 JSON 对象而非自然语言，这是前端可解析的前提。第 **3** 道防线中的"JSON 修复重试"，以及失败重试、分批并发、Semaphore 限流属于 **P10b**。P10 阶段 JSON 解析失败即视为该批次失败并如实记录，不做自动修复 —— 先跑通，再加固。

**模型配置（不写死在代码里）**

| Provider | 配置项 | 说明 |
|---|---|---|
| DeepSeek（主力） | `LLM_PROVIDER=deepseek`、`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL` | 你环境里已配置的 V4.1 Flash 走这里；**模型名从环境变量读，代码里不硬编码**（模型换代时只改 `.env`） |
| Anthropic（备选/对照） | `LLM_PROVIDER=anthropic`、`ANTHROPIC_API_KEY`、`ANTHROPIC_MODEL=claude-opus-5` | 用**官方 `anthropic` SDK**，不要用 OpenAI 兼容 shim。适合做「同一批条款两个模型跑对照」的加分演示 |

> 为什么坚持抽象而不直接调一个 SDK：① 需求要求可替换；② 面试时能讲「模型可插拔、prompt 有版本号、调用有全量日志、失败有降级」这一整套工程化，而不是"我调了个 API"。

### 9.2 审查编排流程（两阶段混合）

**为什么规则 + LLM 混合**：规则引擎**确定性、可解释、零成本、可审计**，适合硬性红线（必备条款缺失、管辖地违规、违约金比例超限）；LLM 适合语义研判（权责是否对等、表述是否模糊、隐含风险）。只用 LLM 会漏掉硬规则且成本高；只用规则无法理解语义。**面试标准答案就是这句。**

```
条款集 (clauses)
   │
   ├─► 2a 规则引擎（并行，毫秒级）
   │     load rule_set(contract_type, is_active)
   │     for rule: evaluator.evaluate(rule, clause, metadata) → RuleHit | None
   │     产出：确定性风险（severity 已定）
   │
   ├─► 2b LLM 语义审查（分批并发，秒~分钟级）
   │     分批：按 clause_type 聚合，每批 ≤ 8 条款 且 ≤ 6000 字符
   │     上下文注入：合同类型 + 我方立场(甲方/乙方) + 该批条款文本(带 clause_id)
   │                    + 规则已命中的提示（让 LLM 不重复报，专注语义）
   │     并发：asyncio.Semaphore 限流（默认 4），单批失败不拖垮整任务
   │     产出：findings[]（含 level/reason/legal_basis/quote/context_before/
   │                       context_after/occurrence_hint/suggestion）
   │
   ├─► 2c 合并与去重
   │     key = (clause_id, dimension, 归一化 risk_title)
   │     同时命中 → source=RULE+LLM，level 取二者较高，reason 合并
   │     LLM 的 quote → 后端按 §10.5 四级作用域算法反查坐标
   │       ★ LLM 永不输出坐标；重复文本必须消歧；找不到时降级到条款级并标记待核对
   │       ★ 坐标反查先于落库，反查结果（anchor_method/anchor_score）一并写入 risk_item
   │
   ├─► 2d 风险评分（scorer.py，纯函数、可单测）
   │     score = Σ(HIGH:40, MEDIUM:15, LOW:5)，封顶 100
   │     综合等级 = max(所有有效风险等级)   ← 高风险一票定级，符合需求 §2.4.4
   │     有效风险 = 排除 review_status=REJECTED；MODIFIED 以人工等级为准
   │     结论：存在 HIGH → REJECT(建议拒绝)；仅 MEDIUM → RECTIFY(需整改)；
   │           仅 LOW/无 → PASS(可通过)
   │
   └─► 2e 建议生成
         优先取 LLM findings 内联的 suggestion
         高风险项额外匹配 standard_clause（按 clause_type + tags 相似度）作为示范条款
         无匹配则用 rule.suggestion_template
         最终写入 risk_suggestion（suggested_text + standard_clause_id）
```

### 9.3 Prompt 版本管理

`llm/prompts/clause_review.v1.md` 之类的文件，**文件名带版本号**，渲染前注入 schema。每次调用把 `prompt_version` 写进 `ai_call_log`。这样"改了 prompt 之后效果变好还是变差"有据可查，也便于把老版本任务重放对比。

  │
  ├─ 2 文本抽取
  │    DOCX: python-docx 遍历 body 元素（段落 + 表格，保持文档顺序）
  │          → block_type=PARAGRAPH/TABLE_ROW，paragraph_index 用真实段号
  │    PDF : PyMuPDF page.get_text("blocks") → 带 bbox
  │          判定扫描件：单页有效字符 < 50 且 (图像覆盖率 > 阈值) ⇒ 视为扫描页
  │          扫描页 → 该页渲染 300dpi PNG → OCR
  │          ⇒ 混合 PDF（部分文字版 + 部分扫描）按页分别处理，这点很多实现会漏
  │    OCR : RapidOCR 输出 [{box, text, score}]
  │          → 按 y 轴聚类成行、按行距聚类成段 → 生成 block
  │          → 记录 bbox + ocr_confidence
  │          → 全文平均置信度 < 0.6 ⇒ blocked(OCR_LOW_QUALITY)
  │
  ├─ 3 归一化（normalizer.py）★
  │    去页眉页脚（跨页重复出现的短行，出现 ≥3 页即判定）
  │    合并 OCR 断行（行尾无标点且下一行首非编号 ⇒ 拼接）
  │    全角/半角、中文空格、连字符统一
  │    保留 raw_text，并生成 normalized_index → raw_index 映射表
  │    ⚠️ 映射表必须在内存中随 block 一起产出：前端高亮用的是归一化坐标，
  │       若用户要"复制原文"，需要用映射表还原，否则复制的字会错位
  │
  ├─ 4 元数据提取（metadata_extractor.py）
  │    规则优先：正则/关键词 → 统一社会信用代码(18位)、金额(¥/元/万元 + 大写)、
  │              币种、日期(YYYY年M月D日 等 6 种格式)、履行期限、生效条件
  │    规则未覆盖字段 → 一次 LLM 调用（结构化输出）兜底，标注 extract_method=LLM
  │    每项都回填 source_block_id + char_start_global + char_end_global + page_number
  │
  ├─ 5 条款切分（clause_segmenter.py）
  │    规则优先：编号模式（第[一二三...]条 / ^\d+\.\d* / ^[一二三]、/ 第X章）
  │             命中 ≥ 3 条 ⇒ 视为结构化合同，走规则切分
  │    规则失败/命中过少 ⇒ LLM 兜底：
  │             把 block 序列（order_index + 前 40 字）给 LLM，要求返回
  │             [{clause_no, title, start_order_index, end_order_index, clause_type}]
  │             后端按 order_index 换算成 block 区间与全局字符区间
  │    兜底再失败 ⇒ 降级为「一段一 clause」，clause_type=OTHER，不阻塞任务
  │
  └─ 6 落库 & 状态推进
        document_block / contract_metadata / clause 批量写入
       current_stage=PARSED → task: parsing → reviewing
```

### 10.2 统一坐标系（全文最重要的设计）

```
document_block:
  order_index=12  page_number=3  paragraph_index=27
  text="第三条 违约责任：任何一方违约，应赔偿对方因此遭受的全部损失…"
  char_start_global=8421   char_end_global=8489

risk_item:
  char_start_global=8452   char_end_global=8470   ← "全部损失"
  page_number=3  paragraph_index=27
```

前端拿 `char_start_global/char_end_global` 做高亮，拿 `page_number` 跳页，拿 `paragraph_index` 在 DOCX DOM 中定位。**全系统只有这一套坐标**，风险/元数据/批注/建议全部复用，避免"四套坐标互相对不上"的经典翻车。

### 10.3 高亮为什么不会错位（面试必答）

1. 坐标系是**后端解析时生成的、稳定的全局偏移**，不依赖前端渲染。
2. LLM 只允许输出 `quote` 原文片段，**不允许输出坐标**；后端用 `text.find(quote)` 反查，找不到就丢弃该条。
3. DOCX 前端用 `docx-preview` 渲染，其段落 DOM 顺序 = 解析时的 `order_index` 顺序，按 `paragraph_index` 索引即可定位（同一文档只解析一次，顺序确定性成立）。
4. PDF 前端用 `pdfjs-dist` 的文本层，`page_number` 定位到页，`char_start_global - 该页首字符全局偏移` 定位到页内字符区间。

### 10.4 DOCX 页码语义（MVP 明确定义）

**第一版绝不伪造 Word 原始页码。** 页码语义按文件类型严格区分：

| 文件类型 | `page_number` | 定位主键 | 前端展示 |
|---|---|---|---|
| PDF（文本层） | ✅ **真实页码**（PyMuPDF 页序，1-based） | `page_number` + 全局偏移 | 「第 N 页 / 共 M 页」，支持页码跳转 |
| PDF（扫描件，走 OCR） | ✅ **真实页码**（渲染时的页序） | 同上 | 同上 |
| 图片（jpg/png） | ✅ 恒为 1 | `paragraph_index` 为主 | 「单页图片」 |
| **DOCX** | ❌ **恒为 NULL** | **`order_index` + `paragraph_index`** | 「第 N 段」+ 自定义视图分页，**禁止出现任何"第 N 页"文案** |

**DOCX 的三条硬性约束：**

1. **后端**：`DocxParser` 一律写 `page_number = NULL`，**不得用任何估算值填充**。"每 40 段算一页"这类假分页会让页码与 Word 实际排版不符，法务按页码翻找不到内容 —— 这比没有页码更糟。
2. **前端**：`DocxPreviewer.vue` 用 `docx-preview` 连续流式渲染，**不显示页码**；顶部显示 `第 N 段 / 共 M 段`（由 `paragraph_index` 驱动）。若为阅读舒适需要分页视图，分页条必须显式标注 **「视图分页（非 Word 页码）」**，且分页位置只由前端视口宽度决定，与后端数据无关。
3. **定位文案按 `locator_type` 分支，不做隐式兜底**：
   - `locator_type = PAGE`：`第 3 页 · 第 27 段`
   - `locator_type = PARAGRAPH`：`第 27 段`（**不写页**）
   - 前端读后端返回的 `locator_type` 字段选择文案，**禁止**用 `page_number is null` 这种隐式判断（否则将来接入其他格式会立刻失效）。

`locator_type` 由 `contract_file.file_ext` 在解析阶段一次性写入（同一文件内恒定），并向下传递到 `risk_item`，前端无需自行推断。

**升级路径（第二版，明确未启用）**：若确需 Word 真实页码，`DocxParser.convert_to_pdf()` 通过 LibreOffice headless（`soffice --headless --convert-to pdf`）把 DOCX 转 PDF，用转换后 PDF 的页序回填 `page_number`。**注意这仍是"LibreOffice 排版下的页码"，与微软 Word 的排版可能有 ±1 页差异**，因此即便启用，前端也应标注为「参考页码」。第一版标记为增强项，不实现。

### 10.5 quote → 坐标反查算法（定位准确性核心）

**问题**：LLM 只输出 quote，坐标由后端反查。但"甲方应于收到货物后 30 日内支付"这类句子在合同里可能重复出现多次，**简单地全文 `text.find()` 会高亮到错误位置**（例如高亮到附件或前文引用，而非真正的风险条款）。

**设计目标：定位必须在语义所属范围内确定；重复文本必须消歧；找不到时降级，绝不错误高亮。**

#### LLM 输出契约（findings 元素新增 3 个定位辅助字段）

```json
{
  "clause_id": 42,
  "risk_title": "付款条件缺失验收前置",
  "level": "HIGH",
  "reason": "...",
  "legal_basis": "...",
  "quote": "甲方应在收到货物后 30 日内支付全部货款",
  "context_before": "第四条 付款方式：",
  "context_after": "乙方应在发货前提供全额发票。",
  "occurrence_hint": 1,
  "suggestion": { "type": "REPLACE", "text": "...", "reason": "..." }
}
```

| 字段 | 必填 | 约束 |
|---|---|---|
| `quote` | ✅ | **必须逐字复制**所属 clause 的文本，禁止改写、禁止用省略号截断 |
| `context_before` / `context_after` | ✅ | quote 紧邻的前后文，各 ≤ 30 字，同样逐字复制 |
| `occurrence_hint` | ❌ | 模型认为这是第几次出现（1-based）。**仅作参考，不作唯一依据** |

#### 四级搜索作用域（由紧到松）

| 级别 | 搜索范围 | anchor_method | 采纳条件 |
|---|---|---|---|
| **L1** | 该 `clause_id` 的 `[char_start_global, char_end_global)` | `CLAUSE_SCOPED` | 作用域内**精确唯一命中**直接采纳；多次命中交 context 消歧 |
| **L2** | 该 clause 覆盖的全部 `document_block` 区间 | `BLOCK_SCOPED` | 同上（L1 未命中或消歧失败时进入） |
| **L3** | 全文（带边界分隔符，见下） | `DOC_GLOBAL` | **仅接受全文唯一命中**；多次命中时只有消歧结论明确才采纳 |
| **L4** | 定位失败 → 降级 | `CLAUSE_FALLBACK` | 条款级定位 + 「定位待核对」，**不做整条高亮** |

#### 裁决顺序（严格按此优先级，命中即返回）

```
① 精确唯一命中                 在 L1 内，其次 L2 内 → 采纳，anchor_score = 1.0
② context 消歧                 作用域内多次命中时启用打分（见下）
                                  分差达标 → 采纳
                                  分差不足 → 进入下一级作用域（L1 失败转 L2，L2 失败转 L3）
③ 全文唯一命中                 L3 内精确且唯一 → 采纳（anchor_method = DOC_GLOBAL）
④ fuzzy 模糊匹配（最后降级候选）
                                仅在 ①②③ 全部失败后启用；
                                相似度 ≥ 0.85 且唯一 → 采纳，anchor_score × 0.9
⑤ 全部失败 → CLAUSE_FALLBACK    条款级定位 + 「定位待核对」
```

**关键约束：fuzzy 永远不是主路径。** 它是精确匹配全部失败后的最后降级候选，且必须满足"唯一"才采纳；fuzzy 命中同样只降级、不猜测。

#### context 消歧打分（仅在第 ② 步使用）

```
同作用域内候选数 n：

n == 1  → 属于第 ① 步（精确唯一命中），直接采纳

n > 1   → 对每个候选 pi 计算上下文相似度：
            0.6 × context_before 在 pi 左侧 60 字窗口内的匹配长度比
          + 0.4 × context_after  在 pi 右侧 60 字窗口内的匹配长度比
          （匹配用最长公共前后缀，容忍归一化造成的个别字符差异）

          取最高分 max_score：
            max_score >= 0.8 且与第二名分差 >= 0.3  → 采纳，anchor_score = max_score
            否则                                    → 本作用域判定失败，进入下一级
```

> **第一原则：宁可降级，不可错标。** 错误高亮（把 A 条款的风险标到 B 条款上）对法务是灾难性的信任损失；而"定位到条款级 + 提示人工核对"是可接受且有礼貌的降级。

#### CLAUSE_FALLBACK 的展示语义（不做整条高亮）

定位失败时**不得**把整条 clause 渲染成风险高亮 —— 那等于向法务宣称"整条都有问题"，本身就是错误信息。正确做法：

- 定位降级到**条款级**：点击风险卡片跳转到该条款的**起始位置**；
- 卡片与高亮层标注 **「⚠ 定位待核对」**；
- 高亮层只用**弱化样式**（左侧边距标记 / 虚线边框）圈出条款范围，**不使用任何风险等级色**，与真正的风险高亮在视觉上明确区分；
- `anchor_score = 0.3`、`anchor_method = CLAUSE_FALLBACK`，计入管理端统计。

#### quote 找不到的全部情形与处理

| 情形 | 判定 | 处理 | 日志级别/码 |
|---|---|---|---|
| quote 为空或长度 < 4 | 无效输入 | 丢弃该 finding | warn `LLM_QUOTE_EMPTY` |
| quote 不在该 clause 内 | 模型改写/幻觉 | 依次下探 L2 → L3 | info `ANCHOR_FALLBACK_LEVEL` |
| 全文都不存在 | 幻觉 | 降级 CLAUSE_FALLBACK，**保留风险但标记低置信** | warn `LLM_QUOTE_NOT_FOUND` |
| 仅中文标点/全半角差异 | 归一化口径不一致 | 先做**宽松匹配**：忽略全/半角、空白、中英标点差异后再 find | info `ANCHOR_LOOSE_MATCH` |
| quote 跨两个 block | OCR 断行 / 段落切分 | 主搜索（带分隔符）失败后，在 `folded_doc_joined` 上找跨段候选，**并校验跨越的边界类型**（见下） | info `ANCHOR_CROSS_BLOCK` |
| OCR 错别字导致不完全匹配 | 扫描件 | 即裁决顺序的**第 ④ 步**（最后降级候选）：用 `difflib.SequenceMatcher` 在窗口内找相似度 ≥ 0.85 且唯一的最长子串作为候选，`anchor_score × 0.9` | warn `ANCHOR_FUZZY` |

#### 两个实现要点

**（1）宽松匹配与折叠索引映射**

归一化阶段已统一全/半角与空白，但 LLM 复述时可能又"标准化"一遍。因此搜索前对 quote 与原文窗口**同时**做一次「折叠」（去掉全部空白、标点统一为英文标点、数字统一半角），在折叠串上定位，再用预存的折叠索引映射表还原回原文坐标。**映射表必须与归一化产物一起存在于同一内存对象中**（§10.1 第 3 步已要求），不得只存折叠串。

**（2）跨 block 搜索：边界分隔符 + 边界映射表**

**不能把 blocks 直接无分隔符拼接** —— 那样会人为制造出原文中并不存在的跨段文本（block_i 的末尾 + block_{i+1} 的开头被粘成一个假 quote），使"精确唯一命中"变成假命中。

正确做法是维护**两份**折叠串，用边界分隔符区分：

```
folded_doc_sep    = block[0] + SEP + block[1] + SEP + ...     # 主搜索用，SEP = "\u0000"（1 字符）
folded_doc_joined = block[0] +      block[1] +      ...       # 仅供跨段候选使用

sep_map[k] = {                                  # 每个 block 边界一条记录
    prev_block_id, next_block_id,
    sep_offset,                                 # SEP 在 folded_doc_sep 中的位置
    boundary_kind,                              # LINE_WRAP | PARA_END
    prev_last_char, next_first_char
}
offsets[i] = (folded_start, folded_end, block_id, char_start_global)
```

- **主搜索一律在 `folded_doc_sep` 上进行**：命中区间天然不会跨越 block 边界，第 ① 步的"精确唯一命中"是真命中。
- **只有主搜索全部失败时**，才在 `folded_doc_joined` 上找跨段候选；此时必须校验它跨越的每一个边界：
  - `boundary_kind = LINE_WRAP`（上一 block 结尾无句末标点，典型如 OCR 断行）→ **允许**，确属真实连续文本；
  - `boundary_kind = PARA_END`（上一 block 以句号/分号/冒号等结尾）→ **拒绝**，判定为拼接产生的假文本。
- `boundary_kind` 在解析阶段由 `normalizer` 一次性判定，随 `sep_map` 与 `offsets` 一起持久化在同一个内存对象中。

坐标还原（命中 `[s, e)` 后）：

```
block_id          = 包含 s 的那个 block
char_start_global = blocks[block_id].char_start_global + (s - offsets[block_id].folded_start)
char_end_global   = 若 e 仍在同一 block 内，同理计算；
                    跨 block 时取结束 block 的对应偏移，区间补齐为两个 block 的完整跨度
```

**性能**：折叠全文与 `offsets` 索引在解析阶段生成一次，按 `contract_id` 缓存在进程级 LRU；单次定位复杂度为 O(出现次数 × 窗口比较)，量级远小于一次 LLM 调用，不构成瓶颈。

**可观测性**：每条 `risk_item` 都落 `anchor_method` + `anchor_score` + `occurrence_index` + `quote_context`。前端对 `anchor_score < 0.8` 或 `anchor_method = CLAUSE_FALLBACK` 的卡片显示「⚠ 定位待核对」角标。管理端统计各 `anchor_method` 占比 —— 若 `LLM_QUOTE_NOT_FOUND` 比例偏高，说明 prompt 需要加强"必须逐字复制"的约束。**这让定位质量成为可量化、可迭代的指标，而不是"感觉还行"。**

## 11. 风险审查流程

（编排细节见 §9.2，此处补判定规则与等级映射，直接对应需求 §2.4.4）

### 11.1 规则维度与预置规则集（seed 数据）

| 维度 | 规则示例 | 类型 | 等级 |
|---|---|---|---|
| 主体资质 SUBJECT | 相对方名称缺失 / 统一社会信用代码缺失 | MISSING | HIGH |
| 主体资质 | 相对方名称与信用代码不匹配 | REGEX | HIGH |
| 金额支付 AMOUNT_PAYMENT | **未设置付款前置验收条件**（付款条款中无「验收合格后」类表述） | EXISTS/MISSING | HIGH |
| 金额支付 | 预付款比例 > 30% | THRESHOLD | MEDIUM |
| 违约责任 LIABILITY | **我方单方承担无限责任**（含「全部损失/无限责任/不设上限」且未限定对方） | KEYWORD | HIGH |

| 违约责任 | 双方赔偿上限不对等 | LLM | HIGH |
| 知识产权 IP | 知识产权归相对方所有（我方采购场景） | KEYWORD | HIGH |

| 保密 CONFIDENTIAL | **缺少保密义务期限** | MISSING | MEDIUM |
| 不可抗力 FORCE_MAJEURE | 未明确不可抗力通知时效 | MISSING | MEDIUM |
| 数据安全 DATA_SECURITY | 缺少数据安全/个人信息保护条款 | MISSING | MEDIUM |
| 验收 ACCEPTANCE | 缺少验收标准 | MISSING | MEDIUM |
| 条款完备性 | 缺少争议解决条款 | MISSING | HIGH |

预置 3 套规则集：`采购合同审查清单 v1`、`销售合同审查清单 v1`、`劳动合同审查清单 v1`。

### 11.2 等级与结论映射

| 综合等级 | 判定条件 | 审查结论 | 前端展示 |
|---|---|---|---|
| 高风险 | 存在任一有效 HIGH | `REJECT` 建议拒绝/重大整改 | 红色，卡片置顶 |
| 中风险 | 无 HIGH，存在 MEDIUM | `RECTIFY` 需整改后签署 | 橙色 |
| 低风险 | 仅 LOW 或无 | `PASS` 可通过 | 绿色 |

**等级可被人工覆盖**：`risk_item.review_status=MODIFIED` 时以人工等级为准，综合等级实时重算，并记录谁在什么时候改的（审计）。

## 12. 审批回写流程

```
法务点击「写回审批意见」
  │
  ├─ 1 组装 content_md（Jinja2 模板，对应需求 §2.4.8）
  │     ## 合同审查意见
  │     **合同名称** / **合同编号** / **送审部门** / **申请人** / **相对方** / **金额** / **履约周期**
  │     ### 一、综合审查结论
  │     总风险等级：高 | 结论：建议拒绝 | 核心风险摘要：…
  │     ### 二、风险清单明细（按等级排序）
  │     1. [高] 知识产权归属供应商 —— 页码 3 / 第 8 段
  │        原文：…
  │        依据：《民法典》第 847 条…
  │        建议修改为：…
  │     ### 三、法务批注
  │     ### 四、审查系统信息（任务号、审查时间、模型、规则集版本）← 可追溯
  │
  ├─ 2 dry_run 预览：POST /tasks/{id}/writeback {dry_run:true} → 返回 Markdown 给前端预览
  │
  ├─ 3 提交：幂等键 idempotency_key = sha256(task_id + content_hash)
  │    writeback_record: not_written → writing
  │    ApprovalClient.post_comment(instance_id, content_md, idempotency_key)
  │
  ├─ 4 结果
  │    2xx → success，记录 external_comment_id
  │    超时/4xx/5xx → failed(记录 error_msg)，waiting 用户重试
  │    幂等键重复 → 返回既有评论，视为 success（不产生第二条）
  │
  └─ 5 重试：POST /tasks/{id}/writeback/retry
       status: failed → writing；attempt+1；超过 3 次提示人工介入
       ⚠️ 重试前先查审批系统是否已有该幂等键的评论（防"写成功了但响应丢了"）
```

**"写成功了但响应超时"这个经典场景**是本设计的重点：靠**幂等键 + 回写前查重**兜底，而不是盲目重试产生重复评论。Mock 审批系统内置 `duplicate_comment` 故障注入来专门演示这个。

## 13. 异常和重试机制

### 13.1 错误分类（ErrorClassifier）

| 类别 | 例子 | 处理 |
|---|---|---|
| **USER_ERROR**（不可重试） | 文件加密、格式不支持、文件损坏、正文为空 | 直接 `blocked`，给出人话原因 + 修复建议，等人工换文件 |
| **DATA_ERROR**（可降级） | OCR 置信度过低、条款切分失败、LLM 返回的 quote 找不到 | 降级处理（走兜底路径）+ 记 warning，**不阻塞任务** |
| **SYSTEM_ERROR**（可重试） | LLM 超时/429/5xx、DB 瞬时连接错误、网络抖动 | 指数退避自动重试 |
| **FATAL** | 配置错误、API Key 无效、依赖缺失 | `blocked` + 告警，这是运维问题不是合同问题 |

### 13.2 三层重试

| 层 | 范围 | 策略 |
|---|---|---|
| L1 传输层 | 单次 HTTP 调用 | SDK 内置重试（Anthropic SDK 默认 `max_retries=2`，自动重试 408/409/429/5xx）+ 我们显式配置 |
| L2 阶段层 | 单个解析/审查单元（如一批条款） | 退避 `min(2^n + jitter, 60s)`，最多 3 次；单批失败不影响其它批 |
| L3 任务层 | 整个 review_task | `retry_count` 上限 3；耗尽 → `blocked` + 记录 `block_reason_code`；人工可再触发 |

**退避必须带抖动（jitter）**，避免多任务同时重试造成惊群。

### 13.3 幂等性

| 场景 | 幂等键 |
|---|---|
| 附件下载/解析 | `file.sha256`（UNIQUE） |
| 任务执行 | `sha256(contract_id + file_sha256 + rule_set_version + prompt_version)` —— 同输入同规则同 prompt 不重复审查 |
| 回写 | `sha256(task_id + content_md_hash)`（UNIQUE） |
| 写接口 | Header `Idempotency-Key` |

### 13.4 超时

| 层级 | 超时 | 超时后 |
|---|---|---|
| 单个 LLM 调用 | 120s（可配） | 该批失败 → L2 重试 |
| 单文件解析 | 300s | PARSE 失败 → L3 |
| 整个任务 | 15min | 强制 `blocked(TIMEOUT)`，释放 worker |
| HTTP 请求 | 前端 30s / 后端接口不阻塞（202） | 前端提示重试 |

### 13.5 卡死任务自愈

Worker 每 30s 心跳写 `review_task.heartbeat_at`。启动时和执行循环中扫描：`status IN (parsing, reviewing) AND heartbeat_at < now() - 5min` ⇒ 判定 worker 崩溃，任务回退 `pending` 重新入队（`retry_count+1`）。这是"进程被 kill 也不会永久卡住"的保障。

### 13.6 日志

- 结构化 JSON 日志（`request_id` / `task_id` / `contract_id` / `stage` 贯穿全链路）；
- `task_event` 表 = 给前端展示的任务时间线（什么时候进什么状态、什么原因）；
- `ai_call_log` 表 = 每次模型调用全留痕（token、耗时、原始响应、prompt 版本）。

## 14. Mock 审批系统设计

### 14.1 定位

真实企业审批系统（如钉钉/飞书/泛微/OA）我们接不到，所以**在本系统内实现一个 Mock 审批模块**，它扮演"外部系统"的角色：

- 有**独立的数据表**（`approval_instance` / `approval_comment`），不与合同表混用；
- 通过 **`ApprovalClient` 抽象接口**访问，与未来接真实系统同签名；
- 有**独立的展示页面**（`MockApprovalView.vue`），可以像外部系统一样被操作。

> 架构意义：Mock 不是"假数据填充"，而是**防腐层（Anti-Corruption Layer）**。面试时可以讲："我们把外部依赖抽象成接口并用 Mock 实现，真实对接时只替换适配器，业务代码零改动。"

### 14.2 模拟的三个能力

| 能力 | 接口 | 说明 |
|---|---|---|
| 待办拉取 | `GET /mock-approval/instances?cursor=&limit=` | 支持游标增量，对应真实系统的分页待办列表 |
| 附件下载 | `GET /mock-approval/instances/{id}/attachment` | 返回本地 `samples/` 里的示例合同文件 |
| 评论写回 | `POST /mock-approval/instances/{id}/comments` | 带 `Idempotency-Key`；重复键返回既有评论不新建 |

### 14.3 故障注入（★ 演示阻塞重试与幂等的关键）

`POST /mock-approval/fault-config`：

| 开关 | 作用 | 演示什么 |
|---|---|---|
| `latency_ms` | 人为延迟 | 超时处理 |
| `fail_rate` | 按概率返回 500 | 任务阻塞 + 自动重试耗尽 → `blocked` |
| `fail_times` | 前 N 次失败第 N+1 次成功 | 重试成功的完整链路 |
| `duplicate_comment` | 写回时先成功但返回超时 | **幂等性验证**（不产生重复评论） |
| `reject_encrypted_file` | 返回一个加密 PDF | `FILE_ENCRYPTED` 阻塞 + 人工重新上传 |

有了这个开关，**"异常任务阻塞与重试流程"（需求 §2.4.7）可以在演示时一键复现**，而不是靠嘴说。

### 14.4 预置数据

`scripts/seed_mock_approval.py` 灌入 4 张审批单：

1. 软件采购合同（知识产权归属供应商 + 到货即付全款无验收）→ **端到端主演示场景**
2. 大额销售合同（我方无限责任 vs 对方每日万分之一）→ 违约责任不对等场景
3. 劳动合同（保密期限缺失 + 竞业限制无补偿）→ 中风险场景
4. 扫描件采购合同（图片 PDF）→ OCR 链路场景

## 17. 项目实施阶段划分

> 每一阶段都遵循你的要求：**先设计 → 再编码 → 再验证**，验证通过才进下一阶段。

### 17.1 最小可运行闭环（黄金链路）—— 最高优先级

**P2 之后的推进原则：先把一条最细的端到端链路跑通并固化，再横向扩展能力。** 禁止出现"PDF/OCR 都做完了但 DOCX 主链路还没通""解析做完了但前端还看不到"这类横向铺开。

```
★ 黄金链路（Golden Path）

  上传 DOCX → 解析(DOCX only) → 落库(document_block / clause)
      → 规则审查 → DeepSeek LLM 审查 → 风险落库(risk_item)
          → 前端展示（合同列表 → 工作台 → 风险卡片 → 原文高亮定位）

  范围界定（刻意收窄）：
    文件格式：只支持 DOCX。PDF / 扫描件 / 图片 一律不接。
    定位精度：block/clause 级 + 段落索引；page_number 恒为 NULL（§10.4）。
    规则集：只启用「采购合同审查清单 v1」中的 3~5 条启发性规则。
    LLM：单一 Provider（DeepSeek），不分批并发，条款串行调用。
    前端：只做 合同列表页 + 工作台双栏 + 风险卡片。大盘/规则配置/模板库全部后置。
    可靠性：状态机 + task_event + 基础重试。心跳自愈、故障注入后置。
    幂等：只做最小核心幂等（见下），不做完整幂等体系。
    明确不做：批注、回写、报告、人工复核状态流转、元数据人工校正。

  最小核心幂等（黄金链路唯一保留的幂等能力）：
    ① 附件级：contract_file.sha256 UNIQUE
       —— 同一文件重复上传不重复解析、不重复计费
    ② 任务级：review_task.idempotency_key UNIQUE
       —— sha256(contract_id + file_sha256 + rule_set_version + prompt_version)，
          同输入同规则同 prompt 不重复审查
    ③ 风险级：risk_item 落库前按 (task_id, clause_id, dimension, 归一化 risk_title) 去重
       —— 防止并发分批或重试导致同一风险重复入库（对应 §9.2 步骤 2c 的合并键）

  后置（不进黄金链路）：回写幂等、报告幂等、通用 Idempotency-Key 中间件。
```

**黄金链路验收标准（一句话）**：把 `samples/采购合同-风险版.docx` 上传后，**5 分钟内**在浏览器工作台看到「知识产权归属供应商」「未设置付款前置验收条件」两条高风险卡片，点击卡片能跳转并高亮到对应段落。

黄金链路跑通后，再按此顺序接入：PDF 文本层 → 扫描件 OCR → 元数据提取增强 → 条款切分增强 → 人工复核与批注 → 审批回写 → 报告导出 → 规则/模板管理页 → 故障注入演练 → 全链路联调与测试。

### 17.3 阶段依赖（修订版）

```
黄金链路（串行，必须按序，每步都要能端到端跑通）：
  P2 → P3 → P4 → P5 → P6 → P7(仅DOCX) → P8(条款切分) → P9(3~5条规则) → P10(串行LLM) → P11(列表+工作台)
                                                                                        │
                                                              ★ 黄金链路验收点 ─────────┘
                                                                                        │
扩展阶段（此后可并行推进）：                                                             ▼
  P7b (PDF文本层 + OCR)  ─┐
  P8b (元数据增强)        ├─→ P11b(大盘/筛选) → P12(回写+报告) → P13(规则/模板管理页)

## 附：关键设计点的面试话术（你在原则 20 里要求的）

| 设计点 | 一句话话术 |
|---|---|
| 为什么规则 + LLM 混合 | "硬性红线用规则保证确定性和可审计，语义研判交给 LLM 保证覆盖面；只用规则会漏语义风险，只用 LLM 会漏硬规则且不可解释、成本高。" |
| 统一坐标系 | "全系统只有一套全局字符偏移坐标系，解析时生成，风险/元数据/批注/建议全部复用，从根上避免多套坐标对不上导致的高亮错位。" |
| LLM 不许自报坐标 | "模型只输出 quote，坐标由后端反查。模型在长文本里数偏移量必然幻觉，把定位权收回到确定性代码里。" |
| 两阶段状态机不可回退 | "审查结论是审计证据，completed 后不可变；重新审查新建任务，历史全留存。" |
| 幂等回写 | "回写的幂等键是 task_id + 内容哈希。最危险的不是失败，是'写成功了但响应超时'导致重复评论——所以重试前先按幂等键查重。" |
| 三层重试 + 错误分类 | "先分类再重试：用户错误直接阻塞等人工，系统错误才退避重试，数据质量问题走降级不阻塞任务。盲目重试只会放大故障。" |
| Worker 心跳自愈 | "任务表带 heartbeat_at，扫描超时任务回退 pending 重新入队，进程被 kill 也不会留下永久卡死的任务。" |
| Mock 审批系统的定位 | "它不是假数据，是防腐层。外部依赖抽象成接口 + Mock 实现，真实对接只换适配器。" |
| 故障注入 | "把超时、失败、重复写回做成可配置开关，异常流程可以一键复现演示，而不是靠截图讲故事。" |
| LLM 结构化输出四道防线 | "协议层约束 + 提示层说明 + 解析层修复重试 + 校验层强校验；最后仍失败就降级为仅规则结果并标记告警，绝不让一个批次拖垮整个任务。" |
| 附件去重 | "文件 sha256 唯一索引，同一份合同重复提交不会重复解析、重复审查、重复计费。" |
| **并发模型边界** | "阻塞调用会卡死整个 event loop。我按'原生 async / to_thread / 独立进程池'三档划分：LLM 和 DB 是 async，解析库是 C 扩展所以走线程池，OCR 这种秒级 CPU 任务走独立进程池——因为 onnxruntime 长时间占 GIL，扔线程池照样拖慢事件循环。心跳也做成独立后台任务，保证 OCR 卡住时不会误判任务死亡。" |
| **抢占事务边界** | "锁只覆盖抢任务那一条 UPDATE。`FOR UPDATE SKIP LOCKED` 抢到行后立刻改状态、写事件、commit，锁就释放了，OCR 和 LLM 全程在事务外跑。用长事务包住长耗时任务会拖垮连接池并产生大量锁等待——这是 DB 当队列时最容易踩的坑。" |
| **quote 消歧定位** | "LLM 只给 quote 不给坐标，后端按'条款内 → 条款的 block 区间 → 全文'四级作用域反查；同一作用域出现多次时用前后文相似度打分消歧，分差不够就降级到条款级并提示人工核对。原则是宁可降级不可错标——法务最不能容忍的是风险卡片指错位置。" |
| **DOCX 页码语义** | "python-docx 拿不到真实页码，因为页码是排版结果不是文档属性。所以第一版 DOCX 的 page_number 恒为 NULL，用段落索引 + locator_type 字段显式区分定位方式，前端不显示任何'第 N 页'文案。宁可承认限制，也不能给法务一个翻不到的假页码。" |
| **黄金链路** | "我先把一条最细的端到端链路跑通——上传 DOCX 到前端看到高风险卡片并高亮定位，然后再横向扩 PDF、OCR、回写、报告。避免出现每个模块都做了一半、但整条链路跑不起来的常见失败模式。" |
