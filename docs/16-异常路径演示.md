## 3. Writeback 状态流转

P15-2 冻结的 `WritebackStatus` 状态机（§6.2 架构文档）：

```text
                  ┌──────────────────────────────────────┐
                  │ 首次发起（NOT_WRITTEN → WRITING）      │
                  ↓                                      │
              WRITING ── post 成功 ──► SUCCESS（终态）     │
                  │                                      │
                  │                                      │
                  └── post 失败 ──► FAILED               │
                                       │                  │
                                       │  重试（att+1）   │
                                       ↓                  │
                                    WRITING ── ... ───► SUCCESS
```

**幂等保护**：

* `idempotency_key = sha256(task_id + content_md_hash)` **全局 UNIQUE**（写库层）
* `UNIQUE(instance_id, idempotency_key)` on `approval_comment`（外部层）
* 同 key 重复写：本地**不会**再插 `writeback_record`（捕获 `IntegrityError` 后
  在新事务重查既有记录）
* 同 key 重复调 API：local `SUCCESS` → `ConflictError(WRITEBACK_ALREADY_SUCCESS)`
  → 409 透传，**不**写第二条

## 4. 幂等语义详解

### 4.1 local `idempotency_key`

* 生成：`writeback_render.compute_idempotency_key(task_id, content_hash)` =
  `sha256(f"{task_id}:{content_hash}")`
* 落表：`writeback_record.idempotency_key`（UNIQUE NOT NULL）
* 含义：**这份审查意见"在写回这件事上"的身份**

### 4.2 external `(instance_id, idempotency_key)`

* 表：`approval_comment`
* 唯一：`UNIQUE(instance_id, idempotency_key)`
* 含义：审批系统里"某条意见在某张审批单上"的唯一标识
* 人工评论（`source=MANUAL`）的 `idempotency_key` 为 NULL，**不受**这条约束
  影响（MySQL 唯一索引不把多个 NULL 视为冲突）

### 4.3 `posted=false` 的含义

来自 `WritebackRunResponse.posted` 字段：

* `true` —— 本次调用**真的**向审批系统发了 `post_comment`
* `false` —— 本次调用**没有**发 `post_comment`，因为 `find_comment` 已经命中
  （外部早已存在该 idempotency_key 的评论）

两种情况最终都让本地走到 `success` —— **`posted` 表达的是"这次调用到底做了
什么 IO"，不是结果状态**。这正是 §12 第 5 步 / §14.3 `duplicate_comment` 故障
注入要演示的：「外部写成功但响应丢失」的可恢复性：第一次 `post_comment` 落库
后抛超时，本地 `FAILED`；第二次 `find_comment` 命中，认回来，`posted=false`，
`success`——**没有产生第二条评论**。

### 4.4 lost response 怎么恢复

```text
T0: post_comment() 真的落库一条评论
    ↓
    外部系统响应超时（ApprovalSystemError）
    ↓
T1: writeback_record: WRITING → FAILED (error_msg=超时)
    ↓
    （caller 选择再调一次）
    ↓
T2: execute_writeback(task_id, client)
    ├── 门禁: current_stage == REVIEWED ✓
    ├── start_writeback: 状态 FAILED → WRITING (attempt+1)
    ├── find_comment(instance_id, key) → 命中已有评论
    └── finish_writeback(success=True, external_comment_id=已有id)
                                          posted=false
```

## 5. Agent BLOCKED

P14-4 的 `_execute_review` 在以下三种结局下都会调 Backend 的
`POST /api/v1/review-tasks/{task_id}/block`：

| 结局 | reason_code | 含义 |
|---|---|---|
| graph 抛异常 | `AGENT_GRAPH_EXECUTION_FAILED` | 图之外炸了（堆栈只进日志） |
| graph 跑完但产出不可用 + error_code 命中 `PARSE_*` | `UNSUPPORTED_FORMAT` / `FILE_CORRUPTED` | 解析阶段不可恢复错误 |
| graph 跑完但产出不可用 + 其它 | `INTERNAL_ERROR` | 兜底 |

**注意**：

* `current_stage` 在失败时**不**前不**后**（P14-5-2 冻结语义）—— 失败
  表达「能走到哪一步」，不是「回退到 UPLOADED」
* `block_reason_msg` 是人话原因，**不**含堆栈（`test_a_background_failure_does_not_leak_a_traceback_to_the_caller`）
* `DOCUMENT_ALREADY_PERSISTED` / `TASK_ALREADY_PERSISTED` 是"幂等命中"——
  任务此前已审完——**不**算作新失败，因此**不**调用 `block`

P16-3 demo 场景 6 直接走 Backend service 路径（`block_task`）演示——不启动
真实 Agent，因为 Agent 的 `_FakeGraph(error=...)` 是测试 fixture，不应耦合到
开发工具脚本里。
